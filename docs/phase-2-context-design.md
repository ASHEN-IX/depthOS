# DepthOS Phase 2.3A — Project context and application ownership

**PHASE 2.3A DESIGN ACCEPTED** for the isolated, synthetic policy scope. Phase 1 remains partially accepted. This proposal uses the version 1 POC-02A observer contract as its baseline. Phase 2.2B can evolve the Rust read projection independently.

## Identity evidence

| Signal | What it establishes | Ownership use |
| --- | --- | --- |
| Observer epoch and runtime ID | A reconciled live window within one authenticated observer incarnation. The runtime counter can repeat in the next incarnation. | Primary in-memory window key. Build the epoch from trusted compositor/session identity and observer run identity, retaining it across a proven same-incarnation reconnect. |
| KWin native UUID | KWin's identity for this window object, when serialized successfully. The constructor allocates a UUID. | Optional same-incarnation corroboration. Duplicate, missing or changed UUID evidence cannot justify restoring an old association. |
| Wayland app ID, KWin desktop-file name, XWayland resource class/name | App family and grouping hints. Wayland clients can set and update app IDs. Desktop Entry IDs identify installed entries using lookup precedence. POC-02A emits KWin's `desktopFileName` as `applicationId`; it need not be a raw xdg-shell ID. | Candidate discovery. Keep namespaces distinct, support missing or truncated values, and resolve known aliases explicitly. A matching desktop entry identifies a launcher, and any rule that depends on stronger identity needs independent verification. |
| PID, executable, ancestry | A PID identifies a process at a particular time and namespace. Start time since boot helps detect PID reuse. Executable and ancestry can be missing, namespace-relative or misleading through wrappers, reparenting and process reuse. | Future verified launcher can use a live process handle or boot/namespace/PID/start-time tuple as one input. Require window-specific attribution to an intended launch. The observer currently exports neither PID nor executable provenance. |
| Parent window | POC-02A's `parentRuntimeId` describes a transient relation within the run. Relations may be missing or change when surfaces unmap. | Optional suggestion only for eligible dialogs. Reject missing, cyclic, self, cross-epoch and excluded chains. Require the current parent's independently confirmed association and a matching observation revision before preparing a hint. |
| XDG activation, X startup notification | Transient activation handoff or launch feedback. A token can be forwarded or ineffective. A launch can reuse an existing process. Neither token is part of the current observer contract. | A future cooperative launch integration may correlate an acknowledged request with a particular window. Timing proximity, an activation token alone and legacy startup notification alone never establish ownership. |
| Native desktops, Activities and outputs | Current compositor placement and context, including sticky or multiple memberships and unknown data. | Optional context hints. A separately configured mapping can propose a project. Switching a desktop, changing focus, or activating a logical workspace cannot transfer ownership. |

The observer reads KWin window state on the session bus and the receiver authenticates the publisher. That authenticates the snapshot source. Client-supplied fields in the snapshot retain their original trust level. A null identity, duplicate app ID or unsupported capability can be legitimate. Never join windows by title, PID, geometry, focus sequence, time adjacency or native UUID across incarnations. See [POC-02A](poc-02a.md), [the observer's serialization](../experiments/kwin-observer/contents/code/main.js), [KWin 6.8.3 Window API](https://github.com/KDE/kwin/blob/3e528155d822d41285a509d09751a88fa956267f/src/window.h), and [KWin window construction](https://github.com/KDE/kwin/blob/3e528155d822d41285a509d09751a88fa956267f/src/window.cpp).

Protocol details are grounded in [xdg-shell protocol XML](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/stable/xdg-shell/xdg-shell.xml), [Desktop Entry file naming](https://specifications.freedesktop.org/desktop-entry/latest/file-naming.html), [Linux procfs documentation](https://docs.kernel.org/filesystems/proc.html), [XDG activation protocol XML](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/staging/xdg-activation/xdg-activation-v1.xml), and [Startup Notification](https://specifications.freedesktop.org/startup-notification/latest/).

A terminal can host tabs or panes with separate projects and remote shells. Its GUI PID cannot describe each shell's changing working directory. An editor can reuse a process across windows or open multiple roots in a single window. A browser's desktop ID identifies the browser family while separate profiles or tasks coexist. Profile configuration can also contain sensitive browsing data. A remote development window represents a local frontend while its project can live on a remote host. Flatpak identity describes a packaged app and can survive many independent project contexts. A compositor window is the granularity of this design. Where the window spans projects, offer an explicit shared assignment or leave it unassigned. Independently started windows with ambiguous context start unassigned. See [KDE Konsole features](https://apps.kde.org/konsole/), [VS Code multi-root workspaces](https://code.visualstudio.com/docs/editing/workspaces/multi-root-workspaces), [VS Code Remote SSH](https://code.visualstudio.com/docs/remote/ssh), [Chromium profile storage](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md), and [Flatpak conventions](https://docs.flatpak.org/en/latest/conventions.html).

## Rules and decision table

Workspaces have stable logical IDs. Claims target an exclusive workspace or an explicitly declared shared set. A shared set grants presentation membership only. Independent claims for two projects must never merge into a shared assignment. Evidence is evaluated for exactly one live eligible window key.

| Conditions, evaluated in order | Result | Explanation |
| --- | --- | --- |
| Missing live window, unreconciled replica or mismatched epoch | **Stale** | The requested observation cannot be used. |
| Protected, unknown protection, skip-taskbar or outside supported classification | **Unknown** | Outside policy scope. |
| Valid user assignment or explicit unassignment | **Confirmed** or **Unknown** | The session-local override takes precedence. Unassignment suppresses automatic fallback for this window. |
| Verified DepthOS launch bound to this particular live window | **Confirmed** | The recorded launch intent and verified surface attribution agree. |
| Exact match for a user-authored policy using a verified, scoped binding | **Confirmed** | The selector and intended workspace set were explicitly configured. A broad app-family rule may generate a suggestion only. |
| Heuristic or valid parent hint | **Suggested** | Advisory, pending explicit acceptance. |
| No eligible evidence | **Unknown** | Keep the window unassigned. |

For any winning tier, a missing workspace in any winning claim yields **Stale**, with no fallback or partial shared assignment. Otherwise, distinct target sets at the top tier yield **Conflicted** and no effective owner. Identical sets agree. Parent and other heuristic hints are peers. Sort sources and alternative target sets for deterministic presentation. No conflict is settled by arrival order, active workspace, signal count or numeric score. Revoking a live claim triggers reevaluation. User unassignment is an explicit suppression override and differs from removing an override to allow normal reevaluation. If a connector changes identity or loses verification, remove its applicable claims and reevaluate against the current snapshot.

## Proposed records

**Durable binding definition** contains a logical binding UUID, schema version, workspace ID or explicit shared workspace IDs, selector type and opaque key, local issuer namespace and selector version, provenance class, state (enabled, revoked, or needs review), revision, and creation/update times. Store only an explicitly approved binding or launch profile definition. Shared membership can use foreign-key rows. Durable selectors should identify a DepthOS launch profile or an app-provided context key with a documented, verified issuer. App family alone may be saved as a user-configured *suggestion rule*. A user confirmation has two distinct choices: assign this live window, or separately save an explicit rebindable rule with reviewed scope. A plain live assignment expires when the window disappears. Profiles retain policy intent; a restart must yield fresh evidence before a new window receives ownership. If no reliable selector exists, ask the user to associate the replacement window again.

**Ephemeral association claim** contains the epoch and runtime ID, source enum, target set, issuer reference, validation scope and lifetime. The prototype accepts prevalidated claims. The future orchestrator should retain source evidence only as long as it is required and scope evidence to an immutable observation and policy revision. A launch claim requires a live, bounded, user-authorized intent, fresh nonreplayed attribution, and a verified mapping to the exact surface. A PID match or successful spawn alone cannot mint that claim, especially for apps that open windows through an existing process. Multiple indistinguishable candidate windows remain unassigned pending review.

**Decision result** contains status, a stable reason code, deduplicated source categories, effective or suggested target IDs, and alternative target sets for conflicts. The production envelope also carries the evaluated window key, observer position and policy/workspace revision for revalidation. Confirmed is evidence-backed ownership for the current window. Suggested is advisory, and stale, conflicted and unknown expose no effective target. Confidence is categorical by construction. Consumer code must check status before reading target IDs. Persist the explicit ops and binding definitions, never a cached decision or an automatic promotion of a suggestion.

## Lifecycle and integration

- **Activation and deactivation.** Changing the selected logical workspace updates DepthOS context only. Associated windows retain their assignments across selection changes. Unassigned windows stay visible in an unassigned view, and shared windows may appear in each explicitly approved context.
- **Manual assignment and conflict.** A user selects a live window and current target IDs. Apply the edit with compare-and-set against the displayed observation and policy revision, replacing the previous override. Resolve concurrent overrides through explicit review. Reassignment does not rewrite app-wide rules. If a window has closed or moved to a new observer epoch before commit, require a fresh selection.
- **Crash or restart.** Drop the old live claim when removal is reconciled. Resolve the replacement independently. Reapply durable intent only when its verified selector matches freshly. A new native UUID, repeated PID or same application ID can never carry the previous live assignment.
- **Reconnect and replacement.** During disconnect, gap or resync, suspend decisions as stale. A freshly reconciled snapshot in an authenticated, provably continuous epoch can retain assignments for still-present keys. On script reload, compositor owner/instance change, incompatible protocol or ambiguous continuity, invalidate the epoch and discard its claims. A different consumer receiver UUID alone does not prove compositor replacement or continuity.
- **Deletion, rename and move.** Delete only through the logical workspace transaction. For a future bindings schema, restrict deletion while durable references exist unless the user explicitly removes or revokes affected bindings in the same transaction. Invalidate live claims and old decision revisions before presenting post-delete results. An open or focused window remains open. Deleting one member of a shared assignment requires review or an explicit edit. World movement and workspace rename retain the workspace ID and its associations. Revalidate any future selector whose scope explicitly depends on the World.

In Phase 2.3B, a Rust coordinator should receive immutable, authenticated and reconciled snapshots through the Phase 2.2 adapter, project allowlisted fields, resolve prepared claims, and call the pure policy function. Supply current logical workspace IDs and binding revisions from the domain service. Stamp decisions with the captured revisions, discard superseded work, and revalidate before accepting a user edit. Reconciliation of sequence gaps and owner changes belongs to the adapter. The policy module owns no observer connection, SQLite transaction or action executor. Keep POC-02A unchanged and treat any missing optional fields in a read projection as unavailable capabilities. If the current Rust projection cannot supply parent or protection flags, disable the dependent decisions or exclude incomplete windows until a versioned read projection can carry them. This contract authorizes only an advisory integration and explicit logical binding operations in a separately scoped implementation.

## Privacy and security

Use an allowlist at the adapter boundary. By default keep ephemeral epoch/run ID, runtime ID, eligibility flags, and optional transient relation. App-family identifiers may be needed by a particular rule producer, so treat them as untrusted, bounded local data and handle truncated or malformed values as unusable. Drop titles, sensitive URLs, document names, CWD, executable paths, browser profile names and paths, remote addresses, command lines, process environments, and activation tokens from the policy payload and logs. Avoid hashing these private attributes as substitutes for redaction. If verified process evidence is later needed, obtain only the scoped identity of an owned launch, retain it in memory, and prohibit scanning other app profiles or probing arbitrary processes. The prototype intentionally ignores even app-family strings at the decision boundary.

Treat IDs as data. Never traverse a workspace root to infer ownership, open stored paths automatically, expand remote paths, or execute command text from metadata. If a later feature needs path access, apply explicit capability checks, symlink-aware containment and user-approved scope at that operation. For any future connector, require a verified issuer and audience, bounded freshness and replay protection. Client assertions and same-user D-Bus transport alone are insufficient against spoofed identities. Do not use ownership as an access-control boundary. A grouping mistake can expose project context in UI, so shared membership must be explicit, suggestions must be reviewable, and display/log surfaces should receive only their required fields. Restrict local storage permissions, omit payloads from telemetry, and retain categorical reason codes rather than raw provenance identifiers in diagnostics.

## Fixtures and verification

Run from the isolated copy:

```bash
python3 -B -m unittest discover -s experiments/context-policy -v
python3 -B experiments/context-policy/verify-isolation.py
```

All **16 synthetic tests passed**. Fixtures cover two editor windows, two same-app terminals sharing a PID, unknown browser profiles, explicit sharing, same-epoch UUID replacement, reused PIDs, invalid parents, reassignment and unassignment, precedence, permutation-stable conflicts, missing application identity, same-epoch reconnect, replacement epoch, deletion with a live window, advisory-only heuristics, redaction and protection. The Python standard-library prototype requires synthetic prepared claims. These tests exercise the policy and projection. Kernel process-handle verification, launch attribution, reconnect authentication, rule persistence and real compositor behavior are future integration responsibilities.

The canonical root was opened for read-only source inventory. The destination was created fresh with mode 0700 using a source allowlist, file-type and credential exclusions, symlink rejection, and three matching SHA-256 inventories (before copy, canonical recheck, and destination). As in Phase 2.2A this verifies the copied content without claiming filesystem-level atomicity. The manifest records the **99-file** baseline. The verifier reports canonical baseline drift separately from protected-copy mismatches and unexpected additions. It does not compare newly added canonical paths. The final check found concurrent canonical changes in Cargo.lock, Cargo.toml, src/lib.rs, src/main.rs and src/observed.rs. All 99 protected copied files matched, with no unexpected additions. Only this document and the files under `experiments/context-policy/` were authored in the copy.

## Open questions for Phase 2.3B

- Which application integrations can reliably attest a context key and bind it to a surface when a single-instance process handles an open request?
- Should shared assignments allow separate context-specific roles, and what UI gives users enough visibility into shared versus unassigned windows?
- Which observer capabilities must its Rust projection expose for eligibility and parent hints, and what identity can safely prove continuity across receiver restarts?
- Should the first persistence iteration accept only explicit launch-profile definitions until a cooperative connector namespace and revocation protocol are designed?

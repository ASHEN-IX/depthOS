# Phase 3.7 compositor-owned prototype

The authority observer owns one immutable pending native snapshot on KWin's thread. It binds a guarded exact `KWin::Window`, focused surface, client and seat, window UUID and generation, compositor incarnation, topology revision, guarded source and destination desktops, Activity and membership, lock observation and a steady-clock deadline. Exact object membership and UUID uniqueness are checked against KWin's current window list. A destroyed object clears its guard; a still-live deleted-for-animation window fails eligibility. Active window and seat keyboard surface must both match.

Lifecycle signals discard the pending proposal on focus, current desktop, active output, topology, Activity, seat teardown, lock, window eligibility or removal. Focus changes can schedule a **fresh** guarded capture after event delivery. The focus-epoch check prevents an earlier queued capture from being used after a subsequent activation. Prior proposals never become pending again. The precise Qt timer wakes the observer, but the steady-clock deadline decides expiry and is rechecked in the same turn. No presenter callbacks, native placement setters, focus setters, assignment writes or persistent sink occur. An observation with missing prompt or unqualified lock remains non-authorizing.

## Built-in synthetic turn

The private patched virtual executable can compile an internal test turn. The private launcher starts an owned fixture child before KWin; the child waits for a pipe message before opening its own surface on the private socket. Only the launcher-selected child is eligible; the exact Wayland peer's kernel-reported PID is checked against the startup candidate, a pidfd is opened while the owned process is alive, and a zero-time poll rejects death or ambiguity. The proposal also pins the exact native client, surface and window objects. A PID, app ID, event, device label or client request does not mint an internal token.

By the time the built-in observer is attached, KWin's `workspaceCreated` signal has called `WaylandServer::initWorkspace` synchronously. In locker-enabled fixture mode the lock observer requires explicit `KSldApp::Unlocked`. KScreenLocker 6.8.3's installed API exposes `Unlocked`, `Locked`, and an `aboutToLock` signal; that signal latches denial and retires pending work even before a lock state change. Locker-disabled fixture mode cannot use false from `WaylandServer::isScreenLocked()` as proof of unlock. Actual lock transitions and multiple seats need separate runtime testing.

The private internal prompt is an opaque fixture-owned QObject with an exact identity and parent check. It is not a rendered prompt or proof of protected prompt ownership. The token binds it and the current proposal pointer without returning through any interface. A synchronous KWin-thread check verifies live state, local peer, lock, deadline, prompt identity and token, retires pending by transferring it to a consumed slot, then increments one in-memory counter. A second call with the same token fails. Holding the consumed object prevents allocation reuse in this run. No production proof, native move, external receipt or persistent result exists. Non-test code paths cannot enter this turn. A lost receipt and uncertain-completion recovery are separate Rust/synthetic evidence; this native one-process counter does not produce a transport acknowledgment, so it has no native uncertain-retry mechanism.

The native observer is independent of the existing deny-only JS/Rust/QML view and the Rust `Authorizer`. Clearing a proposal in KWin and Rust refusing claims are separate facts; a normal view cannot call this prototype's test turn.

The reviewed private KWin run observed lock enabled and unlocked for the owned fixture, counted its internal token once, and refused the second call with that token. The test established synchronous fixture behavior in the running compositor. A visible protected prompt, actual lock transitions and qualified human input remain unverified.

## Coordinator lease design

A future positive authority needs one party to own the entire checkpoint throughout final validation. The safest next experiment is to give the compositor a narrowly scoped, immutable policy checkpoint backed by an explicit Rust lease. Acquisition in Rust freezes the exact coordinator incarnation/epoch, revision, observer stream incarnation, policy and request identity; it returns an expiring or revocable reservation whose operation and audience are exact. The compositor must hold that reservation in its own turn and locally revalidate the complete live native state. A lease client must never treat a timeout or disconnect as permission to commit.

Lease revocation and attempt completion require an ordering contract: if the coordinator can permit conflicting state changes immediately after sending a revocation that KWin has not seen, the lease is unsafe. Either the coordinator waits for known terminal non-dispatch or receipt, or it continues to quarantine affected state after expiry and uncertainty. New compositor and coordinator incarnations cancel pending actions and cannot reuse old identifiers. They must reconcile uncertain old attempts with a durable record before allowing conflicting changes. Lost acknowledgment is never proof that dispatch failed and never permits replay; a mere observed postcondition does not identify the actor. If a durable protocol is needed, crash-cut tests must cover reservation persistence, dispatch, acknowledgment loss and reconciliation before production use.

This branch does not implement a production or cross-process lease. It does not claim that asynchronous IPC preserves a single native turn. An unavailable trusted coordinator or protected input/prompt gate means production denial.

# Phase 3.6 native authority feasibility

**NATIVE AUTHORITY REQUIRES COMPOSITOR CHANGES.** The inspected extension surfaces do not establish the requested protected input, prompt integrity and Rust/coordinator consistency boundary. An internal C++ filter is technically viable, but making its code run in KWin does not protect it from hostile extensions or establish that an event came from a physical human. Production authorization remains deny-only. The accompanying C++ prototype tests guarded object lifetime and a synchronous synthetic counting turn; it is not a loaded KWin component.

## Integration options

- **JavaScript scripting:** retains a live script-visible object and reads current desktop/Activity/window membership, as the existing private tracker demonstrates. It has no authenticated physical input envelope or protected prompt/seat contract. The inspected session-bus scripting interface exports `loadScript`, `loadDeclarativeScript` and unloading. Being in the same UID or owning a service name is not approval. Supported scripting functionality is useful for deny-only observation, not this protected authority. No host change is required for the private fixture. Script API compatibility and user-modifiable code remain deployment concerns. [Workspace wrapper](https://github.com/KDE/kwin/blob/v6.8.3/src/scripting/workspace_wrapper.h), [script registration](https://github.com/KDE/kwin/blob/v6.8.3/src/scripting/scripting.cpp#L671), [script loading](https://github.com/KDE/kwin/blob/v6.8.3/src/scripting/scripting.h#L323).
- **Scripted desktop/Quick effects:** compositor rendering and effect input grabs provide presentation and routing. They do not authenticate approval. In particular `EffectsFilter::keyboardKey` creates a `QKeyEvent` without its source `InputDevice*`; Quick effects forward it to a view. A grab or fullscreen flag is not a protected prompt-integrity boundary against arbitrary loaded code. Supported effect features do not supply the complete requested security contract. [Effects filter](https://github.com/KDE/kwin/blob/v6.8.3/src/input.cpp#L538), [Quick routing](https://github.com/KDE/kwin/blob/v6.8.3/src/effect/quickeffect.cpp#L643), [view forwarding](https://github.com/KDE/kwin/blob/v6.8.3/src/effect/offscreenquickview.cpp#L418).
- **Native C++ effects/plugins:** can run synchronously in-process and, using private internals, retain `QPointer<KWin::Window>`, inspect `Workspace`, the seat and `WaylandServer::isScreenLocked()`. Installed development headers and KWin CMake exports are present. These make compilation plausible, not security qualification. Ordinary effects receive converted keyboard events; deeper input-filter access is private implementation coupling. A hostile native plugin shares address space with the proposed authority. The loader checks a version-specific factory IID, so rebuilding and requalification are required across KWin changes. Packaging such a module into the host is explicitly excluded. [Plugin loader](https://github.com/KDE/kwin/blob/v6.8.3/src/effect/effectloader.cpp#L284), [window lifetime](https://github.com/KDE/kwin/blob/v6.8.3/src/window.h#L351), [filter hooks](https://github.com/KDE/kwin/blob/v6.8.3/src/input.h#L131).
- **Internal input filter and Wayland server:** native events carry device pointers before conversion. KWin owns seat focus and lock state, so an experimental built-in component could inspect them in its turn. No reviewed ingress currently binds backend provenance, exact prompt, physical activation edge, trusted loader policy and immutable coordinator checkpoint. `InputDevice*`, `isVirtual()` or a libinput class check alone do not supply those guarantees. The existing private test starts with `--no-lockscreen`; it cannot qualify locked-session behavior. An internal filter is a candidate patch location, not a supported protected-consent API. [Native events](https://github.com/KDE/kwin/blob/v6.8.3/src/input_event.h), [seat](https://github.com/KDE/kwin/blob/v6.8.3/src/wayland/seat.h), [lock observation](https://github.com/KDE/kwin/blob/v6.8.3/src/wayland_server.cpp#L772).
- **Controlled compositor patch:** strongest future candidate. It can retain the exact live `KWin::Window` and own the whole validation/consume/count operation without IPC. It must additionally constrain extension loading and authority code integrity, preserve source provenance from ingress, own protected rendering and focus, and own a checked coordinator checkpoint. This requires a version-pinned experimental KWin build and ongoing upstream maintenance. No system binary is patched, built or installed in this campaign because the missing security policy is substantive; merely adding a positive callback would bypass it.

No inspected supported surface establishes all requested properties. This is a scoped assessment of the named implementations, not proof that every possible KWin integration is impossible. Private C++ access can implement mechanics, but cannot by itself elevate the trust of injected events, mutable same-UID code or an asynchronously sampled Rust epoch.

## Input provenance results

`KeyboardInputRedirection::processKey` constructs a `KeyboardKeyEvent` retaining `device`, then processes spies/filters. EIS keyboard handling invokes `EisDevice::sendKey`, which emits the same `InputDevice::keyChanged` signal path. EIS pointers similarly emit common device signals. Thus a compositor event is not necessarily physical. At the internal filter an EIS device can be identified by implementation, but this is not an end-to-end protected human-origin attestation. At the ordinary effect keyboard ingress the original pointer has already been discarded. [Keyboard pipeline](https://github.com/KDE/kwin/blob/v6.8.3/src/keyboard_input.cpp#L311), [EIS events](https://github.com/KDE/kwin/blob/v6.8.3/src/plugins/eis/eiscontext.cpp#L338), [EIS device](https://github.com/KDE/kwin/blob/v6.8.3/src/plugins/eis/eisdevice.cpp).

The fake-input backend's authentication implementation sets its device authenticated and contains a security TODO. That gate does not attest a particular approved operation. Libinput's `Device` derives a virtual-device flag from the udev path. This is a useful classification signal; it does not prove physical human action or exclude every upstream injection mechanism. [Fake input](https://github.com/KDE/kwin/blob/v6.8.3/src/backends/fakeinput/fakeinputbackend.cpp#L118), [libinput classification](https://github.com/KDE/kwin/blob/v6.8.3/src/backends/libinput/device.cpp#L449).

Remote/portal and accessibility-origin approval cannot be qualified at the selected Qt ingress. No new EIS, remote, physical-device or accessibility injection campaign was performed; those native provenance cases remain unsupported. Synthetic tests deny claimed EIS/remote/accessibility/Qt/QML/physical/unknown origin labels, which verifies stub policy only. No positive inference comes from a Qt event's delivery, spontaneous flag, timestamp, seat string or device name.

## Required compositor changes and consistency contract

1. Introduce a compositor-owned origin envelope at each backend ingress. Carry an unforgeable internal source category, device/session/seat identity and input serial through every transform; explicitly label EIS, portal/remote, fake, accessibility, Qt and unknown sources. Unknown sources and unqualified device chains deny. A kernel/libinput backend requires a separately established device-access policy, including virtual devices and same-UID injection rights.
2. Build the authority into a qualified compositor security domain, with immutable trusted code/resources and a loader policy that excludes hostile native modules and disallows scripts from modifying authority state or impersonating its prompt. Same-UID bus access is not sufficient isolation. Account for debugger/process-memory access and writable startup configuration under the deployment threat model. If those cannot be constrained, refuse deployment.
3. Own one protected prompt instance, immutable text/operation, exact seat and session, authoritative lock/focus observations and a deliberate confirmation edge at the input filter. Cancel on every intervening loss/change, even if focus or state later returns. Prevent overlay, replacement, click-through and ordinary QObject/QML callback approval. Test real lock transitions in a private compositor with a qualified locker.
4. Retain `QPointer<KWin::Window>`, live workspace membership, incarnation and generation. Check deleted state separately from QObject lifetime. Revalidate UUID uniqueness, exact object, source placement/Activity, topology, destination and eligibility. Use `steady_clock`, one-use terminal state and no nested loop, signals to untrusted callbacks, deferred setter or asynchronous IPC across check/consume/count.
5. Move the authorization-critical checkpoint into this authority's turn, or design a lease protocol in which the Rust coordinator freezes the exact epoch/checkpoint until a terminal compositor receipt or explicit uncertainty resolution. A before/after IPC comparison is insufficient. Lease acquisition, revocation, coordinator crash and unresolved dispatch need explicit state machines; no production lease is implemented here. An authoritative epoch unavailable in the turn means denial. Rendering transport and read-only observer updates remain separate from authority state.

The next engineering decision is to sponsor this constrained upstream/private compositor interface and its deployment trust policy. Until then, preserve deny-only behavior and use the [prototype](phase-3-native-authority-prototype.md) for mechanical regression coverage. Synthetic success cannot qualify full Phase 3 production readiness.

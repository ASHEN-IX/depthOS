## Performance, cleanup and limits

Three capture-paused, input-free, settled 3-second samples in the final run measured approximately **0.67% of one CPU core** with previews, **0%** with previews disabled, **0.67%** closed, at roughly **324,028–324,456 KiB RSS**. These coarse isolated samples do not establish production overhead, a memory-leak bound or displayed FPS. Display presentation timestamp collection remains **PENDING**.

The final launcher inventoried 13 process identities (PID and start ticks), including bus/services/marker children, within its private process group; post-cleanup remaining live processes: **zero**. The interaction cleanup checks pass: sender stopped, observer unloaded, effects unloaded, apps stopped, compositor stopped and packages removed. Independent watchdog testing held Shift in the private sender, stalled the worker, then stopped input, unloaded the owned effect, terminated its private group and removed its package. `cleanup.json` preserves the original recovery result; `process-group-cleanup.json` and host comparisons pass. Repeated post-cleanup recovery is idempotent and performs no effect operation on dead compositor identities.

The final native and final watchdog comparisons report equal configuration/effects/shortcuts/outputs/desktops/Activities/packages and all three currently discovered host windows. The whole-audit configuration comparison reports equality, no changed host keys and **zero changed production files**. No existing KDE preference or application window was restored/rewritten to achieve equality.

A confirmed harness defect was fixed: the old launcher queried two historical UUIDs and treated matching null property dictionaries as preservation. Those UUIDs were already absent before the first native run; their original processes had disappeared, and current Brave/ChatGPT processes started before the native test. Their absence is not counted as successful preservation. A read-only KWayland client now enumerates current UUIDs without creating surfaces, activating windows, capturing content or requesting input; each UUID/PID is checked against KWin.getWindowInfo. Empty/missing/incomplete inventories fail closed. Three regression cases cover this repair. The final native run was repeated after the repair, rather than relabeling earlier null comparisons.

One subsequent watchdog attempt (`run-20261116T022759Z-79dd36`) recovered its private resources and preserved current windows but **failed the host comparison**: its baseline caught active `slide` on a different current desktop; the final sample returned to Desktop 1. The mismatch is retained and not waived or “restored.” A fresh settled-baseline watchdog attempt supplies the accepted complete comparison. The harness performs no host desktop/effect mutation; the observed concurrent transition is not attributed to a cause beyond the evidence. Only disposable private runtime/config/data/cache/state paths and private D-Bus endpoints received test changes.

Source-audited and locally tested does not mean host-native tested. Host portal authorization/input, physical hardware input, mixed-output scaling/hotplug, dynamic Activity lifecycle, touch input, forced keyboard-grab refusal and presentation timing remain pending. X11 and arbitrary future KWin releases are unsupported by this qualification.

## Compatibility decision and POC-02F retry

The structured policy now records **6.8.1: HISTORICALLY_VALIDATED**, **6.8.3: ISOLATED_QUALIFIED**, and independent installed/running classifications in baseline manifests. No broad 6.8.x approval exists. Isolated qualification deliberately does **not** expand the host-preparation allowlist: even a matching 6.8.3 pair is blocked with an explicit isolated-only reason. `hostSessionQualified=false` cannot be mistaken for host acceptance. Existing observer/overview host gates are retained. This is a conservative staged boundary, not an outstanding production incompatibility.

The actual `accept.py --preflight-only` and normal preparation both return code 2 for the current 6.8.3/6.8.1 mismatch. Normal preparation writes only a fresh blocked manifest with `preparationStarted=false`, empty owned resources and `cleaned=true`; it starts no portal, guard, effect, observer or test window. Cleanup/watchdog protections remain independent of version approval.

After an eventual user-controlled ordinary KDE session refresh, recheck installed/running versions and compositor owner/PID/bus identity. Before enabling a matching 6.8.3 host preparation path, explicitly review/update the remaining host-only gates (including `observer-session.fish` and `overview-dev.py`) against this scoped qualification. Generate fresh same-session observer acceptance bound to the current identity/source hash; never reuse the isolated or historical cleaned manifest as permission. Only then may an explicitly authorized POC-02F attempt request KDE's nonpersistent portal consent. Input/capture must wait for the OS grant and its scope checks. Matching versions alone do not grant portal access or complete host sign-off.

No confirmed product incompatibility was found. Production QML/JS/metadata is byte-preserved. Confirmed harness repairs cover stale-window preservation checks and an obsolete renderer label. Changes are confined to qualification harness safety/evidence, explicit compatibility classification/tests and documentation.
